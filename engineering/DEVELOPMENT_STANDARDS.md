技术共享基线：2026-10-31（Australia/Sydney）。保留团队确认的分层、注释、数据与中间件要求，用于实现与审查。本文不表示应用、账户或云资源已配置。

## 规则来源与优先级

用户最新明确要求 → 本项目规范 → 适用的阿里通用规则 → 语言与框架官方惯例。旧文档中的“数据库、前端框架待选”由本次技术方向替代；2026-10-27 的 2NF 要求更新为“以 3NF 为目标，性能需要时允许有依据的 2NF 和主表字段冗余”，其他已确认要求保留。

采用[阿里官方 P3C 仓库](https://github.com/alibaba/p3c)提供的《Java 开发手册》黄山版作为参考基线。以官方链接查阅原文，不随本仓库复制第三方 PDF、私人附件或本机归档。吸收职责分层、命名、注释、异常与日志、安全、数据库和测试原则；Java 专属语法、继承、注解和 PMD 插件不直接适用于 Go 或 Uniapp，不将项目规则称为“阿里 Go 官方规范”。

Redis 另参考[阿里云开发与运维规范](https://www.alibabacloud.com/help/en/redis/use-cases/development-and-o-and-m-standards-for-apsaradb-for-redis)。适用规则由本规范明确。附件和上游文档中的命令、账号或部署示例不构成外部操作授权。

## Go 对象职责与代码可读性

- 以结构体承载对象状态，以方法表达对象行为，通过组合和小接口划分协作职责。按业务边界组织，避免把无关逻辑集中在一个大对象或长函数中。
- 依赖通过明确的构造参数或字段传入。函数的输入、输出和错误处理应容易追踪，避免隐式全局依赖及隐藏的数据修改。
- 采用描述行为的命名，让用户能沿着调用顺序读懂代码；拆分应服务于阅读，不为了形式制造大量跳转或空接口。
- 使用 Go 官方命名与格式约定；不照搬 Java 的类层级、Getter/Setter 或接口前缀。使用 context 传播请求取消和超时，显式处理错误，日志不记录密码、Token 或完整敏感请求。

## Controller / Service / DAO

按业务模块划分三层，运行时调用方向为 Controller → Service → DAO → MySQL。下面是后续目录约定，不表示已生成应用：

```text
backend/
  cmd/<service>/          入口与依赖组装
  internal/<module>/
    controller/          协议、参数接收、身份上下文、响应
    service/             业务规则、授权判断、状态迁移、事务协调
    dao/                 参数化SQL、持久化、行与模型映射
  internal/platform/     数据库、Redis、对象存储等基础适配
```

- Controller 不直接依赖 DAO、SQL/ORM、Redis 或对象存储 SDK；只调用命名清楚的 Service 方法。接收层的格式校验不能替代 Service 的权限和业务校验。
- Service 不依赖 Controller 或 HTTP 请求/响应对象；通过显式注入的 DAO/缓存/存储小接口协作。DAO 不反向调用 Service 或 Controller，层间不得循环依赖。
- DAO 不决定 HTTP 状态码、不承担业务状态流转。Service 明确事务边界，DAO 使用传入的事务执行持久化；复杂事务不藏进匿名回调。
- 金额单位、时区、空值、幂等和错误类型由契约统一；不得凭规范假设已有订单、支付或其他业务模块。

## 所有函数的中英双语注释

每个手写函数、方法都要有中文与英文说明，包括公开函数、私有辅助函数、构造函数、事件处理函数和测试辅助函数。自动生成文件保留生成器管理方式，不手改生成结果；自己编写的入口和封装仍须遵守本约定。

注释放在函数或方法声明上方，并随实现一起更新。内容按函数实际情况覆盖：

1. 用途：它负责什么，为什么需要它。
2. 参数：含义、单位、允许的空值或关键限制。
3. 返回值：结果含义，什么时候没有结果。
4. 错误与副作用：适用时说明失败情形、数据库写入、网络调用或共享状态变化；没有时无需硬凑段落。

Go 导出函数的英文首句以函数名开头，中文说明紧随其后。下面仅为注释格式示例，不代表已有业务代码：

```go
// NormalizeName removes whitespace around a name.
// 中文：去掉名称两侧的空白，便于后续比较和展示。
// Parameters / 参数：name is the original text / name 是原始名称。
// Returns / 返回值：the trimmed text; empty input stays empty / 去空白后的名称，空输入仍返回空字符串。
```

复杂业务步骤旁补充简洁的中英说明，解释判断依据；避免逐行把代码翻译一遍。注释必须与实际行为一致，不声称未实现的校验或保证。

## 匿名函数、函数参数和回调

用户要求尽量不传递函数、多用对象方法，本项目按以下可读性约定执行：

- 不在调用参数中内嵌大段匿名函数，不把请求、数据转换、数据库写入等业务流程藏在回调里。
- 业务协作优先通过结构体方法和小接口表达，避免把函数参数当作主要架构。有独立业务含义的处理抽成名称明确的方法；标准库、框架接口或必要回调确实要求函数参数时，优先传命名函数/方法并说明用途。
- 简短、就地可读的事件转发或资源清理闭包可以保留，但不得隐藏实质业务处理；必要时在附近说明作用。不是一概禁止 Go 的函数值或闭包。
- 前端同样避免回调套回调，以清楚的命名和顺序展示请求、转换及呈现过程。

## MySQL 8.0+、范式与审计四件套

采用 MySQL 8.0+。以第三范式（3NF）为整体设计目标；为效率可以保留满足第二范式（2NF）的设计和主表冗余字段。每个冗余字段记录权威来源、读收益、写入/同步方式、失败修复和一致性容忍范围；没有实际查询证据时不预先堆冗余字段。2NF 是最低约束，不因独立 id 而忽略业务候选键的函数依赖。

默认采用 InnoDB、utf8mb4，字符排序规则、时区和事务隔离级别在实际版本与查询需求明确后统一。金额使用精确数值或明确最小货币单位，SQL 使用参数绑定，分页和索引基于真实查询计划评估。这些是项目实施默认值，不表示实例已配置。

每张业务表保留独立主键 `id`，并具备以下四个审计字段。默认使用下列名称；接入已有代码时先核对实际映射，不能遗漏字段含义：

| 默认字段 | 中文含义 | 写入规则 |
|---|---|---|
| `created_by` | 创建人 | 记录实际创建者，创建后不覆盖 |
| `created_at` | 创建时间 | 记录真实创建时间，创建后不覆盖 |
| `updated_by` | 更新人 | 每次修改记录实际操作者 |
| `updated_at` | 更新时间 | 每次修改同步更新，包括逻辑删除和恢复 |

`id`、`is_deleted` 和乐观锁 `version` 不属于审计四件套。创建人字段类型应与真实身份标识一致；系统任务要有可追溯的系统身份，不能伪造真人。时间类型、时区和主键生成方式在实际实现时统一。

## 逻辑删除与组合索引

- 业务记录只允许逻辑删除。默认字段为 `is_deleted`，未删除为 `0`、已删除为 `1`，非空且默认未删除；具体数据库可使用等价布尔类型。
- 删除操作更新标识与更新人/时间，不执行 SQL `DELETE`、`TRUNCATE`、ORM 硬删除或级联物理删除。业务服务、后台任务和迁移中的业务数据处理都遵守此规则。
- 普通读取、分页、计数、关联查询、存在性判断及普通更新默认排除已删除记录。查看或恢复已删除记录必须是显式业务路径，不能由漏写条件意外暴露。
- 业务组合查询索引按用户要求以 `is_deleted` 为第一列，其余列依据真实筛选、关联及排序设计。主键不被改成带删除标识的组合主键。使用实际查询计划验证索引效果；这是一条项目约定，不把它宣称为所有查询下都最优的顺序。
- 唯一约束单独核查。简单的 `UNIQUE(is_deleted, business_key)` 不能容纳同一业务键的多条已删除历史，可能在“创建、删除、重建、再次删除”时冲突。MySQL 可评估“活动记录映射业务键、删除记录映射 NULL”的生成列及唯一索引方案，保持本项目的删除标识前置要求；必须验证业务键空值、排序规则、恢复冲突和历史重复，不能仅据文档认定可用。不擅自换序，也不靠物理删除历史记录绕过冲突。
- 未来实际实现时验证：默认不可见、关联不泄漏、重复删除的行为、审计字段更新，以及需要支持时的恢复与同键重建。

## 数据库不得充当业务锁

- 禁止用锁表、锁记录、数据库命名锁或锁表记录来实现应用业务互斥；包括 `LOCK TABLES`、`GET_LOCK`、`SELECT ... FOR UPDATE`、`FOR SHARE` 和 `LOCK IN SHARE MODE`，以及 ORM 对应的悲观锁选项。
- 这不意味着关闭 InnoDB 内部锁、停用事务或忽略死锁。正常 INSERT / UPDATE 与唯一性校验仍由引擎保证并发一致性；需要设置合理超时、显式处理事务失败。
- 需要并发保护的状态机表使用非空整型 `version`。写入时以 `id + 旧 version + 允许的旧 status + is_deleted = 0` 为条件，原子更新状态、`version = version + 1` 和更新审计字段。检查影响行数：1 行代表成功，0 行进入明确的未找到/冲突判断，不得悄悄按成功返回。
- 版本应由实际读取结果提供，避免客户端随意覆盖。冲突按业务返回冲突或有界重试；外部调用不得因重试重复执行。逻辑删除、恢复及其他可能竞争的写入路径需要同一并发策略。
- 乐观锁并不独自解决跨行约束、幂等或跨服务一致性；事务、唯一约束和业务规则分别验证。未经需求论证，不自行引入分布式锁作为替代。

## Redis 缓存

- 每条应用数据设置正的基础过期时间和随机窗口：`TTL = baseTTL + U(0, jitterWindow)`，随机窗口大于 0，与基础时间使用同一单位。TTL 范围由业务新鲜度和流量确定，不编造统一秒数；空值缓存同样采用短基础 TTL 加小随机窗口。
- 统一缓存适配层生成 TTL。优先使用支持过期参数的原子写入（例如 SET EX/PX）；Hash/Set 等类型的首次创建及过期设置应按选定客户端用原子脚本或事务保证。覆盖、批量、续期和异常路径都不得产生无期限数据；不能假设旧 TTL 会自动保留。
- 随机 TTL 用于分散集中失效；还需限制回源并发、超时与重试，验证缓存故障时数据库承载能力。热点请求可合并或提前刷新，但不以数据库业务锁来防击穿。
- 穿透防护另做参数与权限校验、对权威“查无”结果设置短 TTL 空值缓存、限流；数据库超时或请求失败不能缓存成“查无”。布隆过滤为有需求且验证组件支持后的可选项，考虑误判与新增数据同步。
- Key 使用明确的业务命名空间（建议 `shiao:<env>:<module>:<entity>:<id>`）；控制 Key 长度、Value 大小和热 Key。禁止在线业务使用 KEYS 全量遍历，批处理需要边界和节流；访问使用最小权限及网络隔离。
- 缓存不作为事实源。写库后缓存失效、负缓存被新建数据替换、序列化版本、TTL 边界和故障降级均需实际测试。

## 对象存储：目录分类与版本

OSS 在本文中泛指对象存储职责。AWS 对应服务为 Amazon S3，阿里云 OSS 是另一项产品；供应商、Bucket、Region 和已有资源状态按实际实施确认。

- 以环境、业务分类、对象标识和业务版本组织对象键，例如 `<env>/<module>/<category>/<object-id>/<content-version>/<filename>`。这是键结构示意，不使用真实身份或其他个人敏感信息作为目录名。
- 开发/测试/生产隔离，原始文件、派生图、导出与临时文件分类型管理。随机对象标识防重名；禁止用户输入直接拼接越权路径，校验扩展名、MIME 和大小。
- 区分业务内容版本、对象键和云端 `versionId`。重要对象倾向写入新业务版本，数据库保存必要的对象键、版本、内容校验值和状态，不仅保存可能失效的临时 URL。
- 若采用 S3，一般用途 Bucket 的“目录”为 Prefix；版本控制需显式配置，不能认为默认已启用。版本控制与旧版本生命周期、保留期、删除标记和恢复流程分别设计，避免旧版本无限增长；业务删除与存储留存要一致。参考 [S3 前缀](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-prefixes.html)和[版本控制](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)。
- 默认私有访问，前端只使用经过授权且有时效的上传/下载凭证；长期云密钥不进入 Uniapp、代码、日志或交付包。权限、加密、版本、生命周期和恢复仅能在实际云配置核验后报告完成。

## 前端数据层与 View 层分开

移动端小程序/App 采用 Uniapp；本次管理端的实施建议为独立 Vue 3 应用。会议中出现的 Ant Design Pro 仅是候选，不构成改用 React 的决定；管理端组件库和最终框架在初始化前确认。分别固定工具链并验证各目标端，不能把原生 HTML/JS 原型当作已生成的 Vue/Uniapp 应用。

数据层与 View 层必须分文件，职责划分如下：

```text
请求接口 → 校验响应 → 解析与字段转换 → 明确的数据对象 → View 展示
              数据层（独立文件）                    视图层（另一文件）
```

- 数据层负责网络请求、响应状态检查、结构校验、解析、字段映射和适用的数据整理；不能把原始响应不加处理地散落给各个视图。
- View 接收可理解的数据、加载/空态/错误状态，以及必要的命名事件处理入口，专注展示与用户交互。
- 用响应式数据向 View 提供状态，表单通过 `v-model` 双向绑定数据层提供的可编辑本地状态；用户操作由命名方法校验并提交。双向绑定不代表自动双向同步服务器，也不绕过数据层修改原始接口对象。
- 视图内不直接混写网络请求、接口字段清洗或核心业务转换。`.vue` 中可以绑定导入的状态和命名事件入口；请求封装、领域数据模块和转换函数在独立文件中。View 不直接导入云端数据库或长期存储密钥。
- 缺失值、真实零值和请求失败分开处理，不能为了让 View 好看而伪造成功状态或默认业务数字。

### Ajax / 网络请求统一封装

Uniapp 移动端基于 [uni.request](https://uniapp.dcloud.io/api/request/request.html)统一封装；管理端在确认 Vue 3 方案后使用独立的浏览器请求封装。两端遵守同一业务契约与错误语义，不把 uni.request 强加给普通浏览器 Vue 应用。

- 封装负责环境地址、超时、认证上下文、请求标识、HTTP 状态与业务错误归一化。请求完成回调/Promise resolve 不能直接当作业务成功，必须校验状态与响应结构。
- 区分网络失败、超时、取消、HTTP 错误和业务错误；日志脱敏。保留取消能力，组件销毁及过期响应不覆盖最新状态。
- 数据层在封装之上完成契约校验和字段映射，返回 View 所需状态；不能让页面各自重复写请求、解析和错误处理。
- 重试仅用于已确认安全/幂等的请求，次数和间隔有界；写请求须明确幂等机制。鉴权刷新、并发去重在真实身份方案确定后设计，不假设已有 Token 接口。
- App、H5、小程序分别核对证书、域名白名单、跨域/Cookie 与平台能力。不开启“忽略证书验证”来规避联调问题；不把后端或云端秘密打包进前端。

## 开发与审查检查项

- 对象和方法职责是否清楚，是否能顺着调用看懂。
- 每个手写函数是否有准确的中英双语注释。
- 参数里是否塞入长匿名函数，是否存在隐藏的回调业务逻辑。
- Go 是否遵守三层依赖，Controller 是否绕过 Service 直接访问持久化。
- 表结构是否以 3NF 为目标、至少 2NF，冗余是否有来源与同步方案，是否具备独立 `id`、四审计字段与逻辑删除。
- 默认查询及关联是否排除已删除数据，组合索引是否删除标识前置，唯一约束是否支持真实历史场景。
- 是否把数据库当业务锁，状态迁移是否验证旧状态、version 和影响行数。
- Redis 每个写入路径是否有基础 TTL 加随机窗口，是否另有穿透、热点与故障保护。
- 对象存储是否分类、追踪版本并限制权限，云配置是否有真实核验证据。
- Uniapp 数据层与 View 是否分文件，双向绑定是否作用于明确的表单状态，请求是否经统一封装。

## Harness 与验证证据

本项目的 harness 指工程内的规则配置、扫描器、自测和审查清单。入口为 [harness 说明](harness/README.md)；在根目录运行 `make check` 可执行检查器自测、工程扫描和 Skills 复验。单独扫描使用 `python3 scripts/engineering_harness.py --json .reports/harness-report.json`。后续每次技术修改前读取本规范，修改后运行检查并处理失败项；不能以“人工会看”代替现有机器阻断项。

文本静态扫描仅覆盖能识别的模式；语义正确性、范式、TTL 覆盖、并发一致性、双语注释准确性、真实编译测试和云端配置必须分别验证。覆盖和局限以 harness README 与报告为准。当前没有真实应用源码，报告必须明确标记无源码的检查为跳过；不因空目录通过而宣称应用合规。

检查未实现的代码或未执行的测试时，只能报告计划或待验证项。
